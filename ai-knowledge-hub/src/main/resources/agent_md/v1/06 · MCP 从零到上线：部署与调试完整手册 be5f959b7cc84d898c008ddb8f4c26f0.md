# 06 · MCP 从零到上线：部署与调试完整手册

<aside>
🎯

面向**从未接触过 MCP** 的读者。每一步都有“执行什么”与“看到什么算成功”。建议按顺序跑一遍，跑完第 4 节你就已经彻底理解 MCP 了。

</aside>

## 1. 先用一分钟建立正确直觉

MCP（Model Context Protocol）本质上就是 **JSON-RPC 2.0 + 一套约定好的方法名**。你可以把它类比成“专为大模型设计的 Dubbo/gRPC”：

| 你熟悉的概念 | MCP 里的对应物 | 说明 |
| --- | --- | --- |
| 服务提供方（Provider） | MCP Server | 你的每个 Python 仿真插件 |
| 服务消费方（Consumer） | MCP Client | 你的 Java 引擎 |
| 接口方法 | Tool | `submit_job` / `validate_params` … |
| 接口文档 | `tools/list` 返回的 `inputSchema` | **可被大模型直接读懂的接口文档** |
| 服务注册中心 | 你的 `application.yml` 里的 `agent.mcp` 列表 | 小团队阶段静态配置就够 |
| 接口文档里的业务说明 | Resource（`sim://…/sop/…`） | SOP、参数手册等长文本知识 |

**为什么不直接用 REST？** 因为 MCP 把“工具发现（`tools/list`）”也标准化了。你的 Java 引擎不需要知道 coventor 有哪些接口——**启动时问一句就拿到全部工具及其 JSON Schema，直接送给大模型**。这就是“插件化”的技术基石。

### 两种传输方式，分别什么时候用

|  | stdio（子进程） | Streamable HTTP |
| --- | --- | --- |
| 启动方式 | Java 拉起 `python -m servers.xxx` | 独立服务，Java 访问 `http://…/mcp` |
| 适用 | 本地调试、单机部署 | **生产推荐**：可独立扩容、远程部署 |
| 优势 | 零网络配置，一启动就能用 | 能放到有仿真许可证的计算节点上 |
| 坐坑点 | Java 重启子进程就挂；日志难收集 | 需处理鉴权、反代缓存（见第 9 节） |

<aside>
💡

**建议路径**：开发阶段用 stdio 快速验证（不用起 HTTP 服务），联调与上线用 Streamable HTTP。前面的 Java 代码两种都已实现，改一行配置就能切。

</aside>

## 2. 环境准备

### 2.1 Python 版本硬要求

MCP Python SDK 要求 **Python ≥ 3.10**。先确认：

```bash
python3 --version    # 必须 >= 3.10，低于 3.10 安装会失败
```

<aside>
⚠️

CentOS 7 自带 Python 3.6，**装不上**。解决方案任选一：①用 conda/miniconda 建 3.11 环境；②编译安装 Python 3.11；③直接用第 8 节的 Docker 方案（最省事，宿主机 Python 版本无关）。

</aside>

### 2.2 创建项目与依赖

```bash
mkdir -p /opt/sim-mcp && cd /opt/sim-mcp
python3 -m venv .venv
source .venv/bin/activate           # Windows: .venv\Scripts\activate
python -m pip install -U pip
```

`requirements.txt`：

```
mcp>=1.12,<2
uvicorn>=0.30
pydantic>=2.7
starlette>=0.37
```

```bash
pip install -r requirements.txt
python -c "import mcp; print(mcp.__version__)"    # 能打印版本即 OK
```

<aside>
🚨

**必须钉死版本区间 `mcp>=1.12,<2`**。SDK 已有 2.x 线，而 2.x 对应的協议修订（`2026-07-28`）**取消了 initialize 握手与 `Mcp-Session-Id`，并新增了必需的路由头**。前面手写的 Java 客户端是按 `2025-06-18` 实现的，混用会直接握手失败。迁移说明见第 12 节。

</aside>

## 3. 第一次启动（stdio 模式，最快验证）

```bash
cd /opt/sim-mcp && source .venv/bin/activate
MCP_TRANSPORT=stdio python -m servers.coventor_server
```

终端会安静地挂住——**这是正确的**，stdio 模式下它在等标准输入。直接把下面三行粘进去（每行一个 JSON，回车）：

```json
{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"manual","version":"1.0"}}}
{"jsonrpc":"2.0","method":"notifications/initialized"}
{"jsonrpc":"2.0","id":2,"method":"tools/list"}
```

看到一大坨 `{"tools":[{"name":"describe_capability",…` 就说明插件完全正常。`Ctrl+C` 退出。

<aside>
✅

这三行就是 MCP 的全部奥秘：**initialize 握手 → initialized 通知 → 业务调用**。你的 Java `McpClient` 做的事情与这三行一模一样。

</aside>

## 4. 启动 HTTP 模式并用 curl 手工跑完全流程

开两个终端。**终端 A** 启服务：

```bash
cd /opt/sim-mcp && source .venv/bin/activate
export MCP_TOKEN=dev-token-please-change
export PLUGIN=coventor
uvicorn app_wrapper:app --host 0.0.0.0 --port 9101
```

另一个端口再起 litho：

```bash
PLUGIN=litho MCP_TOKEN=dev-token-please-change \
  uvicorn app_wrapper:app --host 0.0.0.0 --port 9102
```

**终端 B** 验证。先握手，注意要把响应头打出来：

```bash
curl -i -X POST http://127.0.0.1:9101/mcp \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -H "Authorization: Bearer dev-token-please-change" \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize",
       "params":{"protocolVersion":"2025-06-18","capabilities":{},
                 "clientInfo":{"name":"curl","version":"1.0"}}}'
```

<aside>
🔑

**两个必靠的细节**：①`Accept` 必须同时包含 `application/json` 和 `text/event-stream`，否则服务端直接 406。②从响应头里找 `Mcp-Session-Id: xxxx`，**后续所有请求都必须回带**，不带会收到 400。

</aside>

把拿到的会话 ID 存成环境变量，发送 initialized 通知（正常返回 **202 Accepted 且无 body**）：

```bash
export SID="把上一步响应头里的 Mcp-Session-Id 粘在这里"

curl -i -X POST http://127.0.0.1:9101/mcp \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -H "Authorization: Bearer dev-token-please-change" \
  -H "MCP-Protocol-Version: 2025-06-18" \
  -H "Mcp-Session-Id: $SID" \
  -d '{"jsonrpc":"2.0","method":"notifications/initialized"}'
```

列工具：

```bash
curl -s -X POST http://127.0.0.1:9101/mcp \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -H "Authorization: Bearer dev-token-please-change" \
  -H "MCP-Protocol-Version: 2025-06-18" \
  -H "Mcp-Session-Id: $SID" \
  -d '{"jsonrpc":"2.0","id":2,"method":"tools/list"}' | python -m json.tool
```

真正调一个工具（**注意参数包在 `arguments` 里**）：

```bash
curl -s -X POST http://127.0.0.1:9101/mcp \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -H "Authorization: Bearer dev-token-please-change" \
  -H "MCP-Protocol-Version: 2025-06-18" \
  -H "Mcp-Session-Id: $SID" \
  -d '{"jsonrpc":"2.0","id":3,"method":"tools/call",
       "params":{"name":"validate_params",
                 "arguments":{"workflow_id":"coventor.mems_resonator_modal",
                              "params":{"beam_length_um":200}}}}' | python -m json.tool
```

你会看到 `next_action: "ASK_USER"` 以及缺失参数列表——**这就是后面“自动追问用户”能力的数据源头**。

完整跑一遍提交与轮询：

```bash
# 提交作业，返回 job_id
curl -s -X POST http://127.0.0.1:9101/mcp -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -H "Authorization: Bearer dev-token-please-change" \
  -H "MCP-Protocol-Version: 2025-06-18" -H "Mcp-Session-Id: $SID" \
  -d '{"jsonrpc":"2.0","id":4,"method":"tools/call",
       "params":{"name":"submit_job",
                 "arguments":{"workflow_id":"coventor.mems_pull_in",
                              "params":{"beam_length_um":200,"beam_width_um":20,
                                        "beam_thickness_um":2,"gap_um":2,
                                        "material":"Si","mock_speed":"fast"},
                              "idempotency_key":"manual-test-001"}}}' | python -m json.tool

# 拿上面返回的 job_id 轮询
curl -s -X POST http://127.0.0.1:9101/mcp -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -H "Authorization: Bearer dev-token-please-change" \
  -H "MCP-Protocol-Version: 2025-06-18" -H "Mcp-Session-Id: $SID" \
  -d '{"jsonrpc":"2.0","id":5,"method":"tools/call",
       "params":{"name":"get_job_status","arguments":{"job_id":"粘这里"}}}' \
  | python -m json.tool
```

<aside>
🎓

跑完这一节，你已经把 MCP 的每一层都亲手摸过了。之后 Java 里任何报错，你都能用这几条 curl 快速定位是“服务端问题”还是“客户端问题”。

</aside>

## 5. 用 MCP Inspector 可视化调试（强烈推荐）

Inspector 是官方的图形化调试器，能点击式调工具、看原始报文。需要 Node.js 18+：

```bash
# 方式一：直连已启动的 HTTP 服务
npx @modelcontextprotocol/inspector
# 浏览器自动打开 http://127.0.0.1:6274
# 在页面上选 Transport = Streamable HTTP
#   URL  = http://127.0.0.1:9101/mcp
#   Header 加一行 Authorization = Bearer dev-token-please-change
# 点 Connect → Tools 页签 → 逐个工具填参数试跑

# 方式二：直接拉起本地 stdio server（不用先启 uvicorn）
npx @modelcontextprotocol/inspector python -m servers.coventor_server
```

<aside>
🔎

**用 Inspector 重点看三个地方**：①工具描述是否说人话——它就是大模型能看到的全部信息；②`inputSchema` 的 `required`/`enum`/范围是否完备；③Resources 页签里 `sim://…/sop/…` 能不能读到 SOP 文本。**工具描述写得好不好，直接决定 Agent 智能度上限**。

</aside>

## 7. 生产化：鉴权、并发、日志

```bash
uvicorn app_wrapper:app \
  --host 0.0.0.0 --port 9101 \
  --workers 1 \
  --timeout-keep-alive 75 \
  --log-level info \
  --access-log
```

<aside>
⚠️

**不要随手把 `--workers` 调大。** 多 worker 意味着多进程，而 MCP 会话状态与内存里的作业句柄都是**进程级**的——请求被轮询到另一个 worker 就会报“会话不存在”或“找不到 job”。需要扩容时的正确做法：保持单 worker，开**多个实例不同端口**，并将作业库从 SQLite 换成 MySQL/Redis。

</aside>

环境变量汇总：

| 变量 | 作用 | 示例 |
| --- | --- | --- |
| `PLUGIN` | 本进程加载哪个仿真插件 | `coventor` / `litho` |
| `MCP_TOKEN` | Bearer 鉴权令牌，与 Java 配置一致 | 随机 32 位串 |
| `WORKSPACE` | 产物输出目录 | `/data/sim/workspace` |
| `DB_PATH` | 作业状态库 | `/data/sim/jobs.db` |
| `MCP_TRANSPORT` | `stdio` 或 `http` | 默认 `http` |

## 8. Docker 部署（推荐，绕开宿主机 Python 版本问题）

`Dockerfile`：

```docker
FROM python:3.11-slim

ENV PYTHONUNBUFFERED=1 \
    PYTHONDONTWRITEBYTECODE=1 \
    TZ=Asia/Shanghai

WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -i https://pypi.tuna.tsinghua.edu.cn/simple -r requirements.txt

COPY sim_mcp_common/ ./sim_mcp_common/
COPY plugins/ ./plugins/
COPY servers/ ./servers/
COPY app_wrapper.py .

RUN mkdir -p /data/workspace /data/db
ENV WORKSPACE=/data/workspace DB_PATH=/data/db/jobs.db

EXPOSE 9100
HEALTHCHECK --interval=30s --timeout=5s --start-period=10s --retries=3 \
  CMD python -c "import urllib.request,os;urllib.request.urlopen('http://127.0.0.1:'+os.environ.get('PORT','9100')+'/healthz')"

CMD ["sh", "-c", "uvicorn app_wrapper:app --host 0.0.0.0 --port ${PORT:-9100}"]
```

`docker-compose.yml`：

```yaml
version: "3.8"

services:
  coventor-mcp:
    build: .
    image: sim-mcp:latest
    container_name: coventor-mcp
    environment:
      PLUGIN: coventor
      PORT: "9100"
      MCP_TOKEN: ${MCP_TOKEN:?请先 export MCP_TOKEN}
    ports: ["9101:9100"]
    volumes:
      - ./_data/coventor:/data/db
      - ./_workspace/coventor:/data/workspace
    restart: unless-stopped

  litho-mcp:
    image: sim-mcp:latest        # 同一个镜像，只换 PLUGIN
    container_name: litho-mcp
    depends_on: [coventor-mcp]
    environment:
      PLUGIN: litho
      PORT: "9100"
      MCP_TOKEN: ${MCP_TOKEN:?请先 export MCP_TOKEN}
    ports: ["9102:9100"]
    volumes:
      - ./_data/litho:/data/db
      - ./_workspace/litho:/data/workspace
    restart: unless-stopped
```

```bash
export MCP_TOKEN=$(openssl rand -hex 16)
echo "把这个填到 Java 配置里: $MCP_TOKEN"
docker compose up -d --build
docker compose ps                    # 两个容器都该是 healthy
curl http://127.0.0.1:9101/healthz
docker compose logs -f coventor-mcp
```

<aside>
💡

注意两个服务**共用同一个镜像**，只是 `PLUGIN` 环境变量不同。这就是插件化带来的部署红利：**新增一个仿真类型，只需多一段 compose 配置，不重新构建不改代码。**

</aside>

## 9. systemd 与 nginx（不用容器时）

`/etc/systemd/system/coventor-mcp.service`：

```
[Unit]
Description=Coventor Simulation MCP Server
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=simuser
WorkingDirectory=/opt/sim-mcp
Environment="PLUGIN=coventor"
Environment="WORKSPACE=/data/sim/coventor"
Environment="DB_PATH=/data/sim/coventor/jobs.db"
EnvironmentFile=/etc/sim-mcp/coventor.env
ExecStart=/opt/sim-mcp/.venv/bin/uvicorn app_wrapper:app --host 0.0.0.0 --port 9101
Restart=always
RestartSec=5
StandardOutput=append:/var/log/sim-mcp/coventor.log
StandardError=append:/var/log/sim-mcp/coventor.err
LimitNOFILE=65535

[Install]
WantedBy=multi-user.target
```

```bash
sudo mkdir -p /etc/sim-mcp /var/log/sim-mcp
echo "MCP_TOKEN=$(openssl rand -hex 16)" | sudo tee /etc/sim-mcp/coventor.env
sudo chmod 600 /etc/sim-mcp/coventor.env      # 令牌不进代码库
sudo systemctl daemon-reload
sudo systemctl enable --now coventor-mcp
sudo systemctl status coventor-mcp
sudo journalctl -u coventor-mcp -f
```

nginx 反代（如果需要统一入口或 HTTPS）：

```
location /mcp/coventor/ {
    proxy_pass         http://127.0.0.1:9101/;
    proxy_http_version 1.1;

    # 以下四行对 SSE 致命重要，缺一行都会表现为“卡住不返回”
    proxy_buffering    off;
    proxy_cache        off;
    chunked_transfer_encoding on;
    proxy_set_header   Connection "";

    proxy_read_timeout 3600s;
    proxy_send_timeout 3600s;

    proxy_set_header   Host              $host;
    proxy_set_header   X-Real-IP         $remote_addr;
    proxy_set_header   Authorization     $http_authorization;
    proxy_set_header   Mcp-Session-Id    $http_mcp_session_id;
    proxy_pass_header  Mcp-Session-Id;
}
```

<aside>
🚨

**过 nginx 后最常见的两个坑**：①忘了 `proxy_buffering off;` → SSE 被缓冲，表现为请求一直卡住；②忘了透传与回传 `Mcp-Session-Id` → 握手后第二个请求就 400。

</aside>

## 10. 健康检查与监控

| 探针 | 命令 | 健康表现 |
| --- | --- | --- |
| 进程存活 | `curl -f http://127.0.0.1:9101/healthz` | `{"status":"ok","plugin":"coventor"}` |
| 協议可用 | curl 跑一次 `initialize` | 返回 200 且带 `Mcp-Session-Id` |
| 工具完整 | `tools/list` 数量 | 等于 12（少了就是插件注册漏了） |
| 端到端 | `GET /api/agent/health/mcp` | 各插件 `connected: true` |
| 业务指标 | `SELECT status, COUNT(*) FROM sim_task GROUP BY status` | FAILED 占比突变即告警 |

Java 侧已内置定时重连（`McpClientManager` 的健康检查）：某个 Server 重启后，**不需要重启 Java**，下一个健康周期会自动重新握手并拉取工具表。

## 11. 排错速查表

| 现象 | 真因 | 处理 |
| --- | --- | --- |
| `406 Not Acceptable` | 请求头 `Accept` 没同时包含 `application/json` 和 `text/event-stream` | 两个都带上（Java 侧 `StreamableHttpMcpTransport` 已处理） |
| `400 Bad Request: Missing session ID` | 握手后未回带 `Mcp-Session-Id` | 从 `initialize` 响应头取并缓存；过 nginx 时确认头透传 |
| `404` 或 `Session not found` | Server 重启了，旧会话失效 | 客户端捕获 `McpSessionExpiredException` 后重新握手重试（已内置） |
| `401 Unauthorized` | `MCP_TOKEN` 与 Java 配置不一致 | 两边对齐；注意 `Bearer`  后面有一个空格 |
| 请求一直卡住不返回 | nginx 缓冲了 SSE | 加 `proxy_buffering off;` |
| `tools/list` 返回空 | 插件未注册或 `PLUGIN` 拼写错 | 看启动日志；确认 `PLUGIN` 值 |
| `ModuleNotFoundError: sim_mcp_common` | 工作目录不对 | 必须在 `/opt/sim-mcp` 下启动；systemd 要设 `WorkingDirectory` |
| 工具调用返回“找不到 job” | uvicorn 开了多 worker | 回到 `--workers 1`，或把作业库换成外部存储 |
| 大模型报“工具名不合法” | 工具名不满足 `^[a-zA-Z0-9_-]{1,64}$` | 工具名只用字母数字下划线；前缀用 `__` 拼接 |
| `initialize` 直接 500 | 装成了 `mcp` 2.x | `pip install "mcp>=1.12,<2"` 重装 |

## 12. 新增一个仿真插件的六步清单

<aside>
🧹

这是整套架构最大的价值所在：新增仿真类型 **不需要改一行 Java 代码，也不需要改提示词**。

</aside>

1. 新建 `plugins/tcad_plugin.py`，实现 `SimPlugin` 接口（拄一份 `coventor_plugin.py` 改）。
2. 声明 `WorkflowSpec`：步骤 `steps`、参数 `params`（含单位/范围/枚举/默认值/`ask_hint`）、前置 `prerequisites`、预设 `presets`、产物 `artifacts`。

# 一、先做问题诊断：你其实有 4 个问题，不是 1 个

| # | 子问题 | 该不该交给 LLM？ |
| --- | --- | --- |
| 1 | **意图识别**：用户想跑什么仿真 | ✅ 必须 LLM |
| 2 | **参数抽取 / 补全 / 追问**：参数极多 | ✅ LLM + 确定性校验 |
| 3 | **依赖推导 / 编排**：多步骤、嵌套前置仿真 | ❌ **应该用确定性代码，不要让 LLM 推** |
| 4 | **执行与可靠性**：长耗时、要幂等、要安全 | ❌ 纯工程，复用你现有的任务引擎 |

**整篇回答最重要的一句话：嵌套依赖和执行编排不要让大模型"知道"，要让系统自己知道。** LLM 只负责"听懂人话 + 填参数"，规划和执行交给确定性引擎。这一条决定了你的 Agent 是"能演示"还是"能上生产"。

这也是 Anthropic 在 [Building Effective Agents](https://www.anthropic.com/engineering/building-effective-agents) 里反复强调的：**workflow（预定义代码路径编排）比 agent（模型自主决定路径）更可预测、更一致**，只在真正需要灵活性的地方才让模型自己决策。


# 三、Capability Registry：让大模型"知道流程和参数"的唯一事实来源

你的两个核心疑问（怎么知道流程、怎么知道参数）**答案是同一个东西**：把每个仿真能力做成一份**机器可读的元数据**，而不是散落在 Java 代码和文档里。

## 3.1 元数据模型

## 3.2 关键工程点：Schema 从 Java DTO 自动生成，杜绝文档漂移

**绝对不要手写 JSON Schema。** 用注解从你已有的参数 DTO 生成：

```java
public record Semulator3DParams(
    @JsonSchema(title = "工艺 Deck", description = "工艺流程文件 ID，可从 deck 库选择或由上游任务产出")
    @NotNull String deckId,

    @JsonSchema(title = "网格分辨率", description = "单位 nm。越小越精确但耗时指数增长；" +
                                                  "经验值取最小特征尺寸的 1/3~1/5")
    @DecimalMin("0.5") @DecimalMax("100") @DefaultValue("5.0") Double gridResolution,

    @JsonSchema(title = "求解器模式", description = "fast=快速预览(±10%误差)；accurate=生产精度")
    @DefaultValue("fast") SolverMode solverMode
) {}
```

用 `com.github.victools:jsonschema-generator`（支持 Jackson + Jakarta Validation 模块）在启动时扫描生成，注册进 Registry。这样：

- **Java 代码是唯一事实来源**，参数改了 Schema 自动跟着改；
- 后端校验、前端表单、LLM 的 tool schema **三者永远一致**；
- `description` 字段就是写给模型看的说明书——把工程师脑子里的经验（"取 1/3~1/5"）写进去，模型的准确率会有肉眼可见的提升。

> Anthropic 的经验：做 SWE-bench agent 时，**优化工具描述花的时间比优化主 prompt 还多**。他们提出「Poka-yoke（防呆）」原则——改造参数设计让模型难犯错（例如强制绝对路径而非相对路径）。你的仿真参数同理：**强制显式单位**（`doseMjPerCm2` 而不是 `dose`）、**枚举代替自由文本**、**用 ID 引用代替文件路径**。

# 四、五种实现方式详解

## 方案 A：扁平 Function Calling（每个仿真 = 一个工具）

### 怎么做

把每种仿真注册成一个 tool，参数 schema 直接暴露给模型，模型一次性填完调用。

```java
@Component
public class SimulationTools {
    @Tool(description = """
        运行 SEMulator3D 工艺仿真，输出 3D 器件结构。
        前置：需要 process_deck 产物。若用户未提供，先调用 list_decks 查询。
        典型耗时 30 分钟~6 小时。
        """)
    public RunHandle runSemulator3D(Semulator3DParams params) { ... }

    @Tool(description = "运行 S-Litho 光刻仿真。前置：需要 structure_3d，通常来自 SEMulator3D 仿真。")
    public RunHandle runSLitho(SLithoParams params) { ... }
}
```

Spring AI 的 `@Tool` 注解会自动从方法签名生成 JSON Schema 并注入 prompt。

### 优点

- **最快**，一两天能跑通 demo；
- 生态完备（Spring AI / LangChain4j 原生支持）；
- 简单场景（单一仿真、参数 <15 个）效果就够用了。

### 缺点 & 难点

- ❌ **参数爆炸**：一个仿真 40+ 参数、5 种仿真 = 200+ 参数塞进 context。业界实测 GitHub 官方 MCP Server 光工具定义就吃掉 42,000 token，而**工具数超过 10~15 个之后 agent 准确率就开始明显下降**（[RAG-MCP 论文](https://arxiv.org/abs/2505.03275)：工具检索能把选择准确率从 13.62% 提到 43.13%，同时砍掉一半 prompt token）。
- ❌ **嵌套依赖靠模型自觉**：你只能在 description 里写"前置需要 X"，模型可能忘、可能顺序错、可能重复跑一个 6 小时的任务。
- ❌ **参数默认值靠模型编**：模型很容易给一个"看起来合理"的数值 —— 这在仿真场景是灾难（跑 6 小时得到废结果）。
- ❌ 无法处理"跑 5 个 corner 的参数扫描"这类结构化批量任务。

### 结论

**只适合 POC 或作为最外层的薄壳**，不要作为最终架构。

## 方案 B：Slot-Filling 对话状态机（NL2Form）

### 怎么做

不让 LLM 自由决策，而是走**受控的槽位填充状态机**：

```
① 意图分类（LLM / 分类模型）→ 确定 capabilityId
② 加载该 capability 的 paramSchema → 初始化槽位表 SlotTable
③ LLM 做「抽取」：从对话历史里抽出所有能填的槽位（一次抽多个）
④ 确定性代码算出 missingSlots（必填且无默认值的）
⑤ LLM 做「提问」：按 paramGroups 分组，一次问一组（不是一个一个问）
⑥ 回到 ③ 循环，直到 missingSlots 为空
⑦ 渲染确认卡片 → 用户确认 → 提交执行
```

关键：**LLM 只做"抽取"和"措辞"两件事，"还缺什么"由代码算。**

```java
public record SlotFillResult(
    Map<String, Object> filled,
    List<MissingSlot> missing,     // 代码算出来的，不是 LLM 说的
    List<Violation> invalid,
    List<String> assumptions       // "我默认用了 solverMode=fast"
) {}

public record MissingSlot(
    String path, String title, String type, String unit,
    String question,               // 给用户看的问法
    List<Object> candidates,       // 候选值（来自历史任务统计）
    Object suggestedDefault, String rationale
) {}
```

微软 Copilot Studio 对 slot filling 的最佳实践也是这套：**先从用户首句话里尽可能多地抽取，跳过不必要的提问**，而不是机械地逐个问。

### 优点

- ✅ **可控性最高**，几乎不会漏参数 —— "参数多"这个痛点解得最干净；
- ✅ 对话体验可预测，容易做多轮记忆和"改一下第 3 个参数"；
- ✅ 可以和前端表单混合：Agent 填好 80%，剩下的**直接渲染一个预填表单让用户点**（比一问一答快 10 倍）。

### 缺点 & 难点

- ❌ 天然是**单任务**的，处理"多步骤 + 嵌套"要额外加一层任务编排；
- ❌ 状态机代码量不小，需要处理：中途改主意、跨槽位约束（`gridResolution` 依赖 `minFeatureSize`）、条件必填（选了 `solverMode=accurate` 才需要填 `convergenceTol`）；
- 难点：**跨轮次状态持久化**（对话可能持续几天）、**条件 Schema**（JSON Schema 的 `if/then/allOf` 写起来很痛苦，建议自己定义一套轻量 DSL）。

### 结论

**参数收集环节的最优解**，应该作为组件嵌入到方案 C/D 里，而不是独立方案。

## 方案 C：NL → Plan DSL + 确定性 DAG 引擎 ★ 我最推荐的主线

### 核心思想：Plan-as-Data

LLM **不执行任何东西**，只产出一份**结构化的执行计划（JSON）**；计划的依赖补全、校验、执行全部由确定性代码完成。

### 4 步流程

**Step 1｜LLM 输出 IntentSpec（轻量，不含完整参数）**

```json
{
  "goal": "对 M1 层做光刻仿真，看看 focus 从 -40 到 +40 的工艺窗口",
  "targetCapability": "slitho.litho_sim",
  "knownParams": { "layer": "M1", "focusRange": [-40, 40] },
  "sweep": { "param": "focus", "from": -40, "to": 40, "step": 20 },
  "references": [{ "type": "priorRun", "hint": "上周那个 28nm 的" }]
}
```

**Step 2｜确定性 Planner 做「反向链推导」自动补全前置任务** ← 这就是你问的嵌套问题的答案

```java
/**
 * 反向链（backward chaining）规划：
 * 目标能力需要 artifact X → 上下文里有吗？
 *   有  → 直接绑定
 *   没有 → 在 Registry 里找 produces=X 的能力 → 作为前置节点插入 → 递归
 */
public SimulationPlan plan(IntentSpec intent, PlanContext ctx) {
    Deque<Requirement> stack = new ArrayDeque<>();
    SimulationPlan plan = new SimulationPlan();

    Capability target = registry.get(intent.targetCapability());
    PlanNode root = plan.addNode(target, intent.knownParams());
    target.consumes().stream().filter(Consume::required)
          .forEach(c -> stack.push(new Requirement(root, c.artifactType())));

    while (!stack.isEmpty()) {
        Requirement req = stack.pop();

        // ① 上下文中已有该 artifact（用户上传 / 历史产出）→ 直接复用，不重复跑
        Optional<Artifact> existing = ctx.findArtifact(req.type());
        if (existing.isPresent()) { plan.bind(req, existing.get()); continue; }

        // ② 计划中已有节点产出该 artifact → 复用节点，只加一条边（避免重复跑 6 小时任务）
        Optional<PlanNode> producer = plan.findProducerOf(req.type());
        if (producer.isPresent()) { plan.addEdge(producer.get(), req.node()); continue; }

        // ③ 都没有 → 从 Registry 找生产者，插入前置节点，继续递归
        List<Capability> producers = registry.findByProduces(req.type());
        if (producers.isEmpty()) { plan.addUnresolved(req); continue; }  // 交给 LLM 问用户
        Capability chosen = disambiguate(producers, ctx);   // 多个候选时按偏好/历史打分
        PlanNode up = plan.addNode(chosen, ctx.inferParams(chosen));
        plan.addEdge(up, req.node());
        chosen.consumes().stream().filter(Consume::required)
              .forEach(c -> stack.push(new Requirement(up, c.artifactType())));
    }
    plan.expandSweeps(intent.sweep());   // 参数扫描 → 展开成并行分支
    return plan.topoSort();              // 拓扑排序 + 环检测
}
```

```json

  "nodes": [
    { "id": "n1", "capability": "semulator3d.process_emulation",
      "reason": "slitho 需要 structure_3d，上下文中不存在，自动插入前置任务",

  "sweeps": [ { "nodeId": "n2", "param": "focus", "values": [-40,-20,0,20,40] } ],

  "missing": [
    { "nodeId": "n2", "path": "dose", "title": "曝光剂量", "unit": "mJ/cm²",
      "question": "曝光剂量用多少？（上次同类任务用的是 30）",
      "candidates": [25, 30, 35], "suggestedDefault": 30 }
  ],
  "assumptions": [ "deckId 沿用 run_7731（上周 28nm 任务）", "gridResolution 取默认 5nm" ],
  "estimate": { "duration": "PT4H30M", "nodes": 6, "licenses": 2 }
```

**Step 3｜校验三重门**（见下文 §6.4）

**Step 4｜渲染确认卡片 → 用户确认 → 提交给你现有的任务引擎执行**

### 优点

- ✅ **嵌套/前置任务 100% 由系统保证**，模型完全不需要知道拓扑关系 —— 加一个新仿真类型只要注册元数据，不用改 prompt；
- ✅ **计划可视化、可编辑、可保存、可复用**（存成模板下次直接跑）；
- ✅ **产物复用自动化**：同一个 6 小时的前置仿真在一个 plan 里只跑一次；
- ✅ **可回放、可 diff**：出问题时能精确定位是"LLM 理解错了"还是"引擎执行错了"；
- ✅ 参数扫描 / 批量 corner 这类需求天然支持。

### 缺点 & 难点

- ⚠️ **前期投入大**：Registry 元数据 + Planner + DAG 引擎，是 2~4 周的工作量；
- ⚠️ 需要业务专家配合把每个仿真的 `consumes/produces/preconditions` 梳理清楚（这个梳理过程本身其实很有价值）；
- ⚠️ 难点 1：**歧义消解** —— 一个 artifactType 有多个生产者时选谁？建议策略：用户上下文 > 最近一次成功历史 > 成本最低 > 让用户选；
- ⚠️ 难点 2：**artifact 类型体系设计**。粒度太粗匹配不准，太细组合爆炸。建议 `type + 语义 tag` 二级设计，例如 `structure_3d[node=28nm, layer=M1]`；
- ⚠️ 难点 3：DAG 引擎要处理长任务（数小时）、断点续跑、部分失败重试、幂等。**建议不要自己造轮子**，直接用 Temporal / Camunda 8 / 或者你现有任务表 + 状态机 + 定时扫描。

### 结论

**这是能上生产的架构。** 强烈建议作为主线。

## 方案 D：ReAct / 状态图 Agent（LangGraph4j / Orchestrator-Workers）

### 怎么做

用 [LangGraph4j](https://github.com/langgraph4j/langgraph4j)（LangGraph 的 Java 版，能和 LangChain4j / Spring AI 集成）把 Agent 建成一张**有状态的图**，节点是 LLM 推理或工具执行，边是条件跳转，带 checkpoint 支持人在环中断和恢复。

```java
var workflow = new StateGraph<AgentState>(AgentState.SCHEMA)
    .addNode("understand",  node_async(this::extractIntent))
    .addNode("plan",        node_async(this::buildPlan))       // 可以内嵌方案 C 的 Planner
    .addNode("clarify",     node_async(this::askUser))         // 中断，等用户输入
    .addNode("validate",    node_async(this::validatePlan))
    .addNode("confirm",     node_async(this::humanApproval))   // 中断，等审批
    .addNode("execute",     node_async(this::submitToEngine))
    .addNode("monitor",     node_async(this::pollStatus))
    .addNode("diagnose",    node_async(this::analyzeFailure))  // 失败自愈

    .addConditionalEdges("validate", edge_async(s ->
        s.hasMissing() ? "clarify" : s.hasError() ? "plan" : "confirm"),
        Map.of("clarify","clarify","plan","plan","confirm","confirm"))
    .addConditionalEdges("monitor", edge_async(s ->
        s.failed() ? "diagnose" : s.done() ? "__end__" : "monitor"), ...)
    .compile(CompileConfig.builder()
        .checkpointSaver(new PostgresSaver(ds))       // 长任务必须持久化
        .interruptBefore("execute")                    // 执行前强制人工确认
        .build());
```

对于"多个仿真并行 + 汇总"的场景，用 **Orchestrator-Workers** 模式：中心 LLM 拆解任务，分发给 worker，再汇总结果。

### 优点

- ✅ **表达能力最强**：循环、条件分支、并行、失败自愈、人在环中断恢复都是一等公民；
- ✅ 天然支持"跑完看结果不满意 → 自动调参重跑"这类真正智能的闭环；
- ✅ checkpoint 机制完美匹配你的"任务跑几小时，对话要能续上"的场景；
- ✅ 有 LangGraph4j Studio 可视化调试。

### 缺点 & 难点

- ⚠️ **不确定性最高**：模型自主决策路径，同样的输入可能走不同的路，在仿真这种"跑错一次浪费 6 小时 + 一个 license"的场景风险大；
- ⚠️ 调试成本高，需要配套 tracing（Langfuse / LangSmith / OpenTelemetry GenAI）；
- ⚠️ LangGraph4j 生态成熟度不如 Python 版，社区小、文档少，踩坑要自己填；
- ⚠️ 成本不可控（可能循环几十轮）—— 必须设 `maxIterations` 和 token 预算硬上限。

### 结论

**不要一上来就用。** 正确姿势是：**先用方案 C 把确定性骨架搭好，再用 D 的状态图作为外层壳**，让 LLM 只在"澄清 / 诊断 / 调参重试"这几个真正需要灵活性的节点上自主决策。

---

## 方案 E：Code Mode（LLM 生成受限脚本）

### 怎么做

不给模型 200 个工具，而是给它一套**类型化的 SDK（TypeScript / Python stub）**，让它写代码，在沙箱里执行：

```python
# LLM 生成的代码，在受限沙箱执行
deck = sim.decks.find(node="28nm", layer="M1")
struct = sim.semulator3d.run(deck=deck, grid_resolution=5.0).wait()

results = []
for focus in range(-40, 41, 20):          # 循环、条件、聚合都是免费的
    r = sim.slitho.run(structure=struct, layer="M1", dose=30, focus=focus)
    results.append(r)

sim.report.plot_process_window([r.wait() for r in results])
```

Anthropic 在 [Code execution with MCP](https://www.anthropic.com/engineering/code-execution-with-mcp) 里论证了这套做法：把工具定义变成文件系统上的 SDK，模型**按需 import**，token 消耗可以降 90%+，而且**工具组合能力大幅提升**（循环、过滤、中间结果不进 context）。

### 优点

- ✅ **处理复杂组合逻辑无敌**：参数扫描、条件重跑、多任务聚合分析，写代码是最自然的表达；
- ✅ **Token 效率最高**：中间结果（比如 500 行仿真日志）留在沙箱里，不进 context；
- ✅ 渐进式披露：模型只读它需要的那几个 API 定义文件。

### 缺点 & 难点

- ❌ **安全是最大问题**：必须严格沙箱（gVisor / Firecracker / 容器 + seccomp）、资源限额、网络隔离、审计。Anthropic 自己也承认这些运维开销要和收益权衡；
- ❌ 生成的代码可能"看起来对但逻辑错"，审查成本高（可以强制先 dry-run）；
- ❌ 你是 Java 栈，跑 Python 沙箱要额外一套基础设施。

### 结论

**作为高级用户的"专家模式"很香**，但不适合做面向所有人的默认路径。可以作为 Phase 4 的能力。

---

## 方案 F：MCP Server 化（这是「接入方式」，和 A~E 正交）

把你的仿真能力封装成 [MCP Server](https://github.com/modelcontextprotocol/java-sdk)（Java SDK 已经很成熟，Spring AI 有 `spring-ai-starter-mcp-server` 自动配置，几行 properties 就能起来）。

```
spring.ai.mcp.server.name=simulation-tools
spring.ai.mcp.server.protocol=STREAMABLE
```

### 为什么值得做

- ✅ **解耦**：Agent 换模型、换框架、甚至换成 Claude Desktop / Cursor / 内部 IM 机器人，后端能力一行不用改；
- ✅ MCP 的 **Elicitation（引出）能力**天然支持"工具执行到一半向用户要参数"——这正是你说的"没提供完整就咨询用户"的协议级支持；
- ✅ MCP 的 **Progress Notifications** 天生适配长耗时仿真任务的进度推送；
- ✅ 未来可以让公司其他 Agent 直接复用你的仿真能力。

### 注意

- ⚠️ MCP 不解决编排问题，**依赖推导还是要你自己做**（就是方案 C）；
- ⚠️ Elicitation 需要 **Client 端也支持**，如果你的前端是自研的，得自己实现这个回调通道；
- ⚠️ 有个常见坑：MCP 工具的必填参数没给时，**LLM 会自作主张填空字符串而不是问用户**——所以服务端必须做强校验并返回结构化的"缺什么"，而不是指望模型自觉。

# 五、推荐落地方案：三层混合

```
外层：LangGraph4j 状态图（薄）    ← 只管对话流转、澄清、确认、失败诊断
  ↓
中层：Plan-as-Data（方案 C）      ← LLM 产计划，确定性 Planner 补全依赖 ★ 核心
  ↓
内层：Capability Registry + 现有任务引擎  ← 元数据驱动 + 你已有的执行能力
  ↓
接口：MCP Server 暴露（方案 F）    ← 面向未来解耦
参数收集：Slot-Filling 组件（方案 B）复用于中层
高级模式：Code Mode（方案 E）作为专家出口
```

**给 LLM 的工具只有 6~8 个"元工具"，不是 200 个参数：**

| 工具 | 作用 | 关键设计 |
| --- | --- | --- |
| `search_capabilities(query)` | 语义检索能力 | 只返回 id + 一句话描述，不返回 schema |
| `describe_capability(id, section)` | 按需拿细节 | `section` ∈ `overview\ |
| `find_similar_runs(query, k)` | RAG 历史任务 | ★ 最实用，见 §6.3 |
| `build_plan(intentSpec)` | 生成计划 | 服务端反向链推导 |
| `validate_plan(plan)` | 校验 | 返回结构化 missing/invalid/warnings |
| `preview_plan(planId)` | 渲染确认卡片 | 给用户看的人话摘要 |
| `submit_plan(planId, token)` | 提交执行 | 需要 confirmToken，防止 LLM 擅自执行 |
| `get_run_status(runId)` | 查状态 |  |

这套 `search → describe` 的两段式就是 Anthropic 提出、Spring AI 已内置的 **Tool Search Tool 模式**：初始只给模型一个搜索工具，需要时按需展开工具定义。Spring AI 的实测数据是 **token 降 34%~64%**，同时保持对上百个工具的访问能力。

# 六、逐条回答你的四个疑问

## Q1：怎么让大模型知道"这个仿真嵌套了其他仿真、需要前置任务"？

有三种做法，**建议 2+3 组合，1 只做兜底**：

### ① 写进 description（❌ 不推荐作为主要手段）

```
"运行 S-Litho 光刻仿真。⚠️ 前置：必须先有 structure_3d 产物，
 通常由 SEMulator3D 工艺仿真产生。若没有，请先调用 runSemulator3D。"
```

问题：新增第 6、7 个仿真时 prompt 变成一团乱麻；模型会漏、会顺序错、会重复跑；无法处理"3 层嵌套"。

### ② 结构化依赖声明 + 反向链自动补全（✅ 强烈推荐）

就是 §3.1 的 `consumes` / `produces` + §4-C 的 Planner。

**关键认知转变：你说的"嵌套仿真"本质不是"函数调用嵌套"，而是"产物（artifact）依赖"。** 一旦用 `输入产物类型 / 输出产物类型` 建模，依赖关系就变成了一张图，系统可以自动推导，**模型压根不需要知道**。

好处：

- 新增仿真类型 = 注册一条元数据，**prompt 一个字都不用改**；
- 三层、五层嵌套自动处理；
- 自动做产物复用去重（同一个 plan 里 6 小时的前置任务只跑一次）；
- 前端可以直接把 DAG 画出来给用户看。

### ③ HTN 配方库（✅ 推荐，覆盖"约定俗成的组合流程"）

有些流程不是靠 artifact 推导出来的，而是业务约定的（比如"做 DOE 工艺窗口分析"= 固定的 5 步）。把这些沉淀成 **Recipe（配方 / 复合任务）**：

```json
{
  "id": "recipe.process_window_doe",
  "type": "compound",
  "aliases": ["工艺窗口分析", "DOE 分析", "PW 分析"],
  "description": "标准工艺窗口分析：结构仿真 → 光刻扫描 → CD 提取 → 窗口拟合 → 报告",
  "decomposition": [
    { "step": "s1", "capability": "semulator3d.process_emulation" },
    { "step": "s2", "capability": "slitho.litho_sim", "after": ["s1"],
      "sweep": { "focus": "$focusRange", "dose": "$doseRange" } },
    { "step": "s3", "capability": "metrology.cd_extract", "after": ["s2"] },
    { "step": "s4", "capability": "analysis.pw_fit",      "after": ["s3"] }
  ],
  "exposedParams": ["deckId", "layer", "focusRange", "doseRange"]  // 只暴露 4 个参数！
}
```

**这一招同时解决了"参数太多"的问题** —— 复合任务只对外暴露 4 个参数，其余 100 多个由配方内部固化或推导。这是让 Agent 好用的最大杠杆。

> 我的建议：**先把你们 80% 的高频任务做成 10~20 个 Recipe。** 这比让 Agent 从零编排要可靠得多，也更符合工程师的心智模型（他们本来就是照着 SOP 跑的）。
>

## Q2：怎么让大模型知道运行某个仿真需要的全部参数？

### ① JSON Schema 作为唯一契约（从 Java DTO 自动生成，见 §3.2）

### ② 参数分层，不要一次全给模型

```
required   (3~6 个)   → 必须问清楚
common     (5~10 个)  → 有默认值，但可能需要调
advanced   (30+ 个)   → 默认隐藏，只在用户明确提到时才拉出来
derived    (N 个)     → 由其他参数计算，模型完全不用管
internal   (N 个)     → 模型不可见（路径、license server 等）
```

`describe_capability(id, section="params", level="required")` 默认只返回必填的。**Agent 从来不需要一次看到 200 个参数。**

### ③ 参数字典 + 向量检索（应对"参数别名"问题）

工程师会说"曝光量""dose""剂量""能量"，都指 `doseMjPerCm2`。建一张参数别名表 + embedding 索引，做 NL → 参数名的映射，比让模型硬猜准得多。

### ④ 元工具而不是大 Schema

```
LLM: describe_capability("slitho.litho_sim", section="params", level="required")
→ 服务端返回精简的 6 个必填参数（带单位、范围、默认、说明、候选值）
```

这就是 RAG-MCP / Tool Search Tool 的思路：**按需加载，而不是全量灌注**。

### ⑤ 值域和枚举一定要给模型

```json
{ "name": "solverMode", "enum": ["fast", "balanced", "accurate"],
  "enumDescriptions": {
    "fast": "10 分钟，±10% 误差，用于快速试错",
    "accurate": "4 小时，生产精度，用于最终验证" } }
```

模型选枚举比填自由文本准确率高一个数量级。

## Q3：用户没提供完整参数时怎么咨询用户？

### 核心原则：**"还缺什么"由代码算，不由模型判断。** 模型只负责把缺失项翻译成人话。

### 完整闭环

```
用户: "帮我跑个 M1 层的光刻仿真"
  ↓
LLM 抽取 → IntentSpec { capability: slitho, knownParams: {layer:"M1"} }
  ↓
Planner 建图 → 发现缺 structure_3d，自动插入 semulator3d 前置节点
  ↓
validate_plan() → 服务端返回结构化缺失清单 ⬇
```

```json
{
  "status": "INCOMPLETE",
  "missing": [
    { "nodeId": "n1", "path": "deckId", "title": "工艺 Deck", "type": "string",
      "question": "用哪个工艺 deck？",
      "candidates": [
        { "value": "std_28nm", "label": "28nm 标准流程（你上周用过）", "score": 0.9 },
        { "value": "std_14nm", "label": "14nm 标准流程" }
      ],
      "widget": "select" },
    { "nodeId": "n2", "path": "doseMjPerCm2", "title": "曝光剂量", "type": "number",
      "unit": "mJ/cm²", "range": [10, 60],
      "question": "曝光剂量用多少？",
      "suggestedDefault": 30,
      "rationale": "你最近 8 次 28nm M1 任务的中位数是 30",
      "widget": "number" }
  ],
  "invalid": [],
  "warnings": [ "预计总耗时 4.5 小时，将占用 2 个 license" ],
  "autoFilled": [ { "path": "gridResolution", "value": 5.0, "source": "default" } ]
}
```

### 5 条实操经验

1. **批量问，不要一个一个问。** 把 `missing` 按 `paramGroups` 分组，一次问一组（≤4 个）。工程师最烦被机器人连问 8 遍。
2. **能猜就先猜，然后声明假设。** 输出 `assumptions: ["gridResolution 取默认 5nm", "deckId 沿用上周的 std_28nm"]`，让用户"看到并可否决"，比"逐个确认"体验好 10 倍。
3. **对必填参数绝不编造。** 在 system prompt 里写死："`missing` 中的参数**必须**向用户询问，**禁止**自行赋值或填空字符串。" 并且服务端做强校验兜底 —— 这是 MCP 场景下一个已知的高频坑：**模型会拿空字符串填必填参数**，只能靠服务端校验挡住。
4. **用 Generative UI 代替纯文字问答。** 让 Agent 返回一个**预填好的表单卡片**（就是你现有的前端表单，只是字段被 AI 填好了），用户扫一眼、改两个数字、点确认。这是"参数极多"场景的最佳交互形态，也让"Agent 填错"的风险降到最低。
5. **Elicitation 协议化。** 如果走 MCP，用 [Elicitation](https://gofastmcp.com/servers/elicitation) 机制在工具执行中途向用户要输入；如果是自研，就实现一个 `ask_user(question, schema)` 工具 + 前端阻塞式回调。

## Q4：怎么让 Agent 又智能、成功率/安全系数又高？

### 🔵 智能度（让它像老工程师）

**① 历史任务 RAG —— 投入产出比最高的一招**

真实场景里 90% 的请求是「**跟上次那个一样，但改两个参数**」。所以做 **Clone + Patch** 模式：

```
用户: "跟上周那个 28nm 的一样，但把 dose 改成 35"
  ↓
find_similar_runs("28nm 光刻 上周") → run_7731（含全部 187 个参数）
  ↓
clone(run_7731) + patch({doseMjPerCm2: 35})
  ↓
diff 卡片: "基于 run_7731，仅修改：曝光剂量 30 → 35 mJ/cm²，其余 186 项不变"
  ↓
用户点确认
```

**参数完整性 100%，用户输入 1 句话。** 这一招基本上单独就能让 Agent「可用」。把历史任务的 `{意图描述 + 参数快照 + 结果指标 + 成败}` 全部向量化入库。

**② 参数默认值分四级取，优先级从高到低**

```
用户显式指定 > 同用户最近成功的同类任务 > 团队/项目模板 > Schema 默认值
```

并在卡片上标注每个值的来源（`paramSources`），透明度直接决定用户信任度。

**③ 失败自愈**：把常见报错映射成诊断规则（`ERR_MESH_TOO_COARSE` → 建议 `gridResolution` 减半重跑），Agent 读到日志后给出可一键执行的修复计划。

**④ 结果解读**：任务跑完后自动分析产物（CD 均匀性、工艺窗口大小），用自然语言总结 + 给下一步建议。这是 Agent 相比表单最大的增量价值。

### 🔴 可靠性 & 安全性（12 条清单）

| # | 措施 | 说明 |
| --- | --- | --- |
| 1 | **LLM 永不直连执行** | 只产 Plan，执行必须过 `submit_plan(planId, confirmToken)` |
| 2 | **三重校验门** | ①JSON Schema ②业务规则/物理约束（`grid ≤ minFeature/3`）③Dry-run 预检（解析 deck、查 license、估资源） |
| 3 | **强制人在环确认** | `riskLevel≥medium` 或预估耗时 > 30min / 成本 > 阈值 → 必须人工确认。确认卡片用**人话**：做什么、跑几个任务、多久、花多少 |
| 4 | **幂等键** | `hash(capabilityId + normalizedParams + inputArtifactIds)`，重复提交直接复用结果 —— 对 6 小时任务这是刚需 |
| 5 | **配额与熔断** | 单会话最大任务数、最大 CPU 小时、license 占用上限、日预算 |
| 6 | **权限下沉** | Agent 用**用户自己的身份**调后端 API，绝不用超级账号。ACL 在 L4 再校验一次 |
| 7 | **计划快照 + 审计** | 存 `{对话原文, IntentSpec, Plan, 用户确认记录, 执行结果}` 全链路，可回放可追责 |
| 8 | **自治等级分档** | L0 只推荐不执行 → L1 单步需确认 → L2 低风险自动/高风险确认 → L3 全自动。**从 L0 上线，按数据逐步放开** |
| 9 | **输出约束** | 结构化输出（JSON Schema constrained decoding）+ 温度 0 + 重试时降级到更强模型 |
| 10 | **循环硬上限** | maxIterations、token 预算、wall-clock 超时，三重刹车 |
| 11 | **Prompt 注入防护** | deck 文件名、用户上传内容、仿真日志都是**不可信数据**，进 prompt 前做隔离标记，绝不当指令执行 |
| 12 | **Eval 回归集** | ★ 攒 100~300 条真实语料 → 标注期望 Plan → 每次改 prompt/schema 跑一遍。指标：意图准确率、参数 F1、计划拓扑正确率、澄清轮数、无确认执行率（必须 0） |

> 第 12 条是最容易被跳过、但最决定长期成败的。**没有 Eval 集，你每改一次 prompt 都是在赌博。**
>

# 八、Java 技术选型

| 需求 | 推荐 | 理由 |
| --- | --- | --- |
| LLM 接入 + Tool Calling | **Spring AI**（你若是 Spring Boot） | `@Tool` 注解、多模型可移植、内置 Tool Search Tool 应对工具膨胀、有 MCP starter |
| 备选 | LangChain4j | 更轻量，非 Spring 项目友好 |

| JSON Schema 生成 | victools/jsonschema-generator | Jackson + Jakarta Validation 模块 |
| 校验 | networknt/json-schema-validator | 服务端强校验 |
| 向量库 | pgvector（你有 PG 就直接用） | 历史任务 RAG + 参数别名检索 |
| 对外协议 | **MCP Java SDK** / spring-ai-starter-mcp-server | 解耦、Elicitation、进度通知 |
| 可观测 | Langfuse / OpenTelemetry GenAI 语义约定 | trace 每次 LLM 调用、工具调用、token |

> **另一个务实选项**：Agent 层单独用 Python 写（LangGraph 生态成熟太多），通过 MCP / HTTP 调你的 Java 后端。你们本来就有 Python 脚本栈，团队接受度可能更高。**Java 后端只需要新增一套 Registry API + Plan API 即可**，不用引入 AI 依赖。这个方案的解耦度和迭代速度往往更好。

# 十、最容易踩的坑

1. **一上来就上 Multi-Agent。** 你这个场景一个 Agent + 好的工具设计足够，多 Agent 只会放大不确定性和调试成本。
2. **把 200 个参数塞进 tool schema。** 工具超过 10~15 个、schema 超过几千 token，准确率就开始崩。用元工具 + 渐进式披露。
3. **让 LLM 判断"还缺什么"。** 它会说"参数齐了"然后填一堆空值。必须服务端算。
4. **没有确认环节直接执行。** 一次错误的 6 小时仿真就够让用户永久放弃这个功能。
5. **参数没有单位。** `dose=30` 到底是 mJ/cm² 还是 J/m²？字段名里带单位，防呆。
6. **手写 JSON Schema。** 三个月后必然和 Java DTO 不一致，然后 Agent 开始神秘失败。
7. **artifact 类型体系设计过细。** 先粗后细，用 tag 做二级区分。
8. **忽略幂等。** 用户重发一句话就多跑一个 6 小时任务 + 多占一个 license。
9. **对话状态只存内存。** 仿真要跑几小时，用户明天回来对话必须还在。
10. **没有 Eval 集就迭代 prompt。** 改一个字，另外三个场景悄悄挂了，你还不知道。
